# SEO & Metadata

## Site config

`src/lib/site.ts` (`siteConfig`) is the **single source of truth** for SEO —
name, description, origin URL, OG image, Twitter handle, theme colour. The
metadata generator, `robots.ts`, `sitemap.ts`, and the JSON-LD helper all read
from it. **Update the placeholder values per project.** `#todo`

`siteConfig.url` comes from `NEXT_PUBLIC_SITE_URL` (see [[environment-variables]]),
falling back to `http://localhost:3000`.

## Metadata generator

`src/utils/seo/generate-page-metadata.ts` exports two builders:

```ts
import {
  generateMetadata,
  generateViewport,
} from "@/utils/seo/generate-page-metadata";

export const metadata = generateMetadata({ title: "…", description: "…" });
export const viewport = generateViewport();
```

- `generateMetadata(props?)` → a Next.js `Metadata` object: title/description,
  OpenGraph, Twitter cards, canonical, icons, robots. `metadataBase` is **always
  set** from `siteConfig.url`, so relative URLs (OG image, canonical) resolve to
  absolute — required by social scrapers.
- `generateViewport()` → the `Viewport` export. `themeColor` lives here, **not**
  on the metadata object (Next deprecated it there).

Accepted `generateMetadata` options: `title`, `description`, `url`, `ogImage`,
`twitterHandle`, `author`, `siteName`. (`keywords` and the non-standard `other`
tags were dropped — no SEO value.)

## robots.txt & sitemap.xml

Generated by the Next file conventions:
- `src/app/robots.ts` → `/robots.txt` — allows all crawlers, points at the sitemap.
- `src/app/sitemap.ts` → `/sitemap.xml` — the home route, one entry per case study
  derived from `projects.filter((p) => p.hasPage)` rather than hand-listed, and
  `/photography`. Adding a project with a page adds its sitemap entry automatically.

## Per-page metadata

`src/views/work/metadata.ts` exports `projectMetadata(slug)` and
`src/views/photography/metadata.ts` exports `photographyMetadata()`. Both read the same
`data/` entries the page renders and return a `Metadata` object. Routes call them rather
than building metadata inline, which keeps `app/**` importing only from `views/`
([[routing]]) and makes it impossible for a share card and its page to disagree.

## Structured data (JSON-LD)

`src/utils/seo/structured-data.ts`:

- `getSiteStructuredData()` → a `Person` + `WebSite` graph. This site is a person, not
  an organisation. The root layout renders it once.
- `getProjectStructuredData({ title, summary, slug, period })` → a `CreativeWork` whose
  author points at the root `Person` node by `@id`, so a crawler resolves the author
  without a second copy of the profile on every page. Rendered by the
  `ProjectSchema` component on each `/work/*` page.

`/photography` deliberately emits none. An `ImageGallery` with zero images is worse
than no markup at all; add it with the first real frame. [[decisions-log]] ADR-0020.

## Bot detection

`src/utils/is-bot.ts` exports `isBot()` — a **server-only** async helper that
reads the `user-agent` header and returns `true` for Lighthouse, Googlebot,
PageSpeed, HeadlessChrome, GTmetrix, Pingdom, Bingbot, Yandexbot.

> [!caution]
> Calling `isBot()` (or any `headers()` reader) in a route **opts it out of
> static prerendering** — a TTFB cost for every visitor. Serving crawler-specific
> behaviour also borders on cloaking. Prefer the [[animation-system|reduced-motion]]
> path (`<ReducedMotion>`): animations only touch opacity/transform, so content
> is always in the DOM and crawlers see it regardless. Use `isBot()` sparingly.

## Static assets

The `public/` **root** holds meta/PWA/SEO assets — favicons (multiple sizes),
Android/Apple icons, `manifest.json`, `browserconfig.xml`, `open-graph.png`.
Site **content** assets (images, videos) go under `public/assets/<section>/` —
see [[folder-structure]].
